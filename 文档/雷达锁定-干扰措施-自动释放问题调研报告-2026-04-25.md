# 雷达锁定/干扰措施/自动释放问题调研报告（2026-04-25）

## 调研范围
- 问题1：玩家雷达锁定敌机，敌机无锁定告警；但 gunner 锁定时告警正常。
- 问题2：雷达锁定后，目标释放箔条和 ECM 不会脱锁。
- 问题3：被雷达制导武器锁定时，载具会自动释放箔条/ECM；希望该行为归属 gunner 逻辑，而不是玩家驾驶逻辑。

本次仅做代码侧排查与根因分析，不改动逻辑。

## 结论总览
- 问题1：**高概率是“玩家锁定链路依赖客户端上报，gunner 锁定链路是服务端直报”导致的稳定性差异**，并且玩家链路多一道“操作者合法性校验”，更容易被拦截。
- 问题2：**根因明确**：服务端 STT 威胁发射逻辑未结合目标反制状态；客户端脱锁判定又依赖本地实体可见性（BVR 场景易失效），导致“看起来不脱锁”。
- 问题3：**根因明确**：自动释放在 `MCH_MissileDetector` 的通用锁定告警路径中触发，取的 `operator` 优先是 0 号位（驾驶员），且仅判断 `getIsGunnerMode(operator)`；驾驶员进入 gunner 模式时会触发自动释放。

## 问题1排查：玩家锁定无告警，gunner 正常

### 1. 两条锁定上报链路不对称
- 玩家雷达锁定上报：
  - 客户端发包：`PacketRadarLockState.handleServerSide -> reportRadarTracking(...)`
  - 代码：`src/main/java/mcheli/network/packets/PacketRadarLockState.java`
- gunner 锁定上报：
  - 服务端直接调用：`MCH_EntityGunner -> reportGunnerTracking(...)`
  - 代码：`src/main/java/mcheli/mob/MCH_EntityGunner.java`

### 2. 玩家链路存在额外拦截条件
- `reportRadarTracking(...)` 中会校验：
  - 载具有人：`isAircraftMannedForEmission(ac)`
  - 上报玩家是否“在该机位上”：`isReporterControllingAircraft(ac, reporter)`（`getSeatIdByEntity(reporter) >= 0`）
  - 代码：`src/main/java/mcheli/MCH_RWRThreatManager.java`
- 若该校验失败，玩家锁定不会进入 `trackingReports`，后续 `emitLockThreatForEmitter` 不会发 STT 威胁。

### 3. 为什么 gunner 看起来更稳定
- gunner 链路在服务端直接拿到 `targetEntity`，并写入 `gunnerTrackingReports`。
- `emitLockThreatForEmitter(...)` 会优先读 `trackingReports`，其次读 `gunnerTrackingReports`。当玩家链路失效时，gunner 仍可驱动告警。

### 4. 本问题当前判断
- 从代码结构看，问题1更像是**玩家上报链路被条件拦截或上报中断**，而非 RWR 告警渲染本身故障。
- 建议用现有雷达调试日志确认：
  - 关注 `trackingReports` / `gunnerTrackingReports` 实时值。
  - 关注 `RWRLOCK ... source=packet_report|gunner_report` 输出来源。

## 问题2排查：箔条/ECM 不导致脱锁

### 1. 服务端 STT 发射未检查目标反制状态（根因）
- `emitLockThreatForEmitter(...)` 仅根据 tracking report 和阵营/RWR能力发 STT。
- 未看到“目标正在 ECM/箔条中则抑制 STT”的服务端判断。
- 代码：`src/main/java/mcheli/MCH_RWRThreatManager.java`

### 2. 客户端虽有“反制导致掉锁”，但依赖目标实体本地可解析
- 客户端掉锁判定路径：
  - `getTrackingInvalidReason(...) -> isTargetCountermeasureActive(...)`
  - `isTargetCountermeasureActive(...)` 通过 `world.getEntityByID(info.entityId)` 拿实体，再判断 `isECMJammerUsing/jammingTick/ecmJammerUseTime/chaffUseTime`。
- 若目标在本地世界中拿不到实体（常见于远距/BVR信息态），该分支返回 `false`，客户端不会因反制而掉锁。
- 代码：`src/main/java/mcheli/render/MCH_RenderRWR.java`

### 3. 结果表现
- 在“本地实体不可见 + 服务端不校验反制”的组合下，会出现：
  - 锁定状态持续；
  - 目标侧 STT 告警持续；
  - 玩家体感为“打箔条/ECM不脱锁”。

## 问题3排查：自动释放归属错误

### 1. 自动释放触发点
- `MCH_MissileDetector.update()` 在雷达相关威胁分支调用：
  - `tryAutoReleaseCountermeasure(lockOperator, true);`
  - `tryAutoReleaseCountermeasure(var4, true);`
- 代码：`src/main/java/mcheli/aircraft/MCH_MissileDetector.java`

### 2. operator 选择优先驾驶员
- `lockOperator/var4` 的选取都是：
  - 先 `this.ac.getRiddenByEntity()`（0号位/驾驶员）
  - 再回退 `this.ac.getEntityBySeatId(1)`
- 因此自动释放天然优先绑定驾驶位操作者。

### 3. 放行条件是“是否 gunner mode”，不是“是否 gunner seat”
- `tryAutoReleaseCountermeasure(...)` 内：
  - `if (!this.ac.getIsGunnerMode(operator)) return;`
- `getIsGunnerMode(entity)` 对 0 号位的语义是：驾驶员若开启 gunner mode，则返回 true。
- 这会导致“驾驶员开启 gunner mode 时，也会触发自动释放”，与“只归属 gunner 逻辑”的期望不一致。
- 代码：
  - `src/main/java/mcheli/aircraft/MCH_MissileDetector.java`
  - `src/main/java/mcheli/aircraft/MCH_EntityAircraft.java`

## 额外观察（与问题相关）
- `MCH_MissileDetector` 内 `Tracking/LockOn` NBT 标记当前仅见读取与清除，未见同模块内设置入口，说明锁定告警主链路已更多依赖新的 RWR Threat 同步体系，而非旧标记位。

## 建议的后续修复方向（不含本次实现）
- 问题1：
  - 给 `reportRadarTracking(...)` 增加更细粒度调试日志（拦截原因、seatId、acId、targetId）。
  - 重点验证玩家场景是否存在 `getSeatIdByEntity(reporter) == -1` 或上报中断。
- 问题2：
  - 在服务端 `emitLockThreatForEmitter(...)` 增加目标反制状态门控（至少 ECM/箔条窗口内抑制 STT）。
  - 或将反制状态通过实体信息同步到客户端，避免仅靠本地 `getEntityByID`。
- 问题3：
  - 自动释放触发主体改为“真实 gunner 座位/实体”而非“任意处于 gunner mode 的操作者”。
  - 若要保留驾驶员 gunner mode 的部分能力，建议拆分独立开关（例如 `pilotAutoCountermeasureWhenGunnerMode`）。
