# 导航状态坦克卡障与飞机脱困调研（2026-04-18）

## 1. 你反馈的问题（确认）

- 你说的是 `gunner` 驾驶坦克执行航路点导航（`NAVIGATE`）时的赶路状态。
- 现象是：战斗状态下遇到高障碍会改出，但导航赶路状态更容易卡住。

该反馈和现有代码行为是吻合的。

## 2. 代码现状结论

### 2.1 坦克并非“没有高障碍检测”

坦克已有前方高障碍判定与大转向改出：

- `hasTooHighObstacleAhead(tank)`：前方采样，若障碍高度 `h > stepHeight` 判定为“过高障碍”。
- 命中后触发 `startLargeTurn(...)` 进行大角度改向。

对应代码：

- `src/main/java/mcheli/mob/MCH_EntityGunner.java`
  - `hasTooHighObstacleAhead(...)`
  - `updateTankDrive(...)` 中的 `blockTooHigh` 分支

### 2.2 导航状态比战斗状态更容易卡住的关键差异

`updateTankDrive(...)` 里，战斗与导航分支存在“脱困强度”差异：

- 战斗分支有额外“周期性大转向”注入（`combatCycleReset` 后触发 `startLargeTurn`）。
- 导航分支没有这套周期性强制改出，主要是“目标朝向修正 + 油门控制”。
- 当 `nav.navigateActive && nav.suppressLargeTurnInNavigate` 时，会抑制一部分“无位移触发的大转向”脱困路径（该路径是另一条独立自救逻辑）。

结果就是：在复杂障碍几何下，导航状态可能持续“轻微修正但出不来”，而战斗状态靠更强的机动扰动更容易摆脱。

### 2.3 为什么“明明有高障碍检测，仍然会卡”

高障碍检测属于局部前探采样，不是完整路径规划，存在漏检边界：

- 前探距离固定（近距离采样）。
- 横向采样点较稀疏。
- 只基于局部方块碰撞高度和 `stepHeight` 判断。

当障碍形状复杂（斜角、边缘、组合墙体、局部可碰撞体）时，可能进入“未判定高障碍但实际过不去”的状态。

## 3. 飞机部分现状（补充）

- 目前飞机 `gunner` 驾驶逻辑没有“连续位移不足 N tick 自动脱困”的专门机制。
- 主要是目标追踪、状态机和实体紧急避让。
- 也没有“按向心侧目标滚转角”明确控制项，滚转更多是由左右转向输入间接产生。

## 4. 建议修复方向（下一步可实施）

### 4.1 针对“导航坦克卡障”的优先修复

在 `NAVIGATE` 状态增加“进度停滞脱困器”（独立于战斗分支）：

- 记录最近 `T` tick 的导航进度（到 waypoint 的水平距离是否下降）。
- 若连续 `T` tick 距离几乎不下降（或位移不足阈值），触发一次导航专用大转向改出。
- 改出期间短暂提高转向优先级，避免“朝向修正”立刻把车头拉回原死角。

建议默认参数（可后续配置化）：

- `NavStuckCheckTick = 80`
- `NavStuckMinMove = 4.0`（水平累计位移）
- `NavUnstuckTurnAngle = 120~180`
- `NavUnstuckCooldown = 60`

### 4.2 坦克前探增强（次优先）

- 增加前探距离层（例如扩到 2~8 格）。
- 增加横向采样密度。
- 增加“可通过高度窗口”判断，降低复杂边角漏检。

### 4.3 飞机可选增强（后续）

- 增加位移停滞脱困（按位移，不按油门）。
- 增加转向时向心侧滚转目标角控制（bank-to-turn）。

## 5. 本次结论摘要

- 你的观察是准确的：问题重点在**导航赶路状态**。
- 代码里“高障碍改出”存在，但导航状态的“强制脱困扰动”弱于战斗状态。
- 下一次改动应优先补“导航停滞脱困器”，这是最直接解决你当前卡障问题的方案。
