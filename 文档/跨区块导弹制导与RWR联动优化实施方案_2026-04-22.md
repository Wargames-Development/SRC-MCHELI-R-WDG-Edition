# 跨区块导弹制导与RWR联动优化实施方案（2026-04-22）

## 1. 文档目的与适用范围
- 本文用于解决“雷达可见/可锁，但导弹在超视距或跨区块条件下不制导”的实战问题。
- 文档面向后续接手开发者，目标是做到“拿到文档即可开工”，并能在多人服务器场景中闭环验证。
- 本文覆盖：
- 导弹（主动/半主动/被动）跨区块制导链路稳定性；
- 数据链中继与目标快照融合；
- RWR与雷达状态一致性（诊断与日志）；
- 分阶段实施、验收、回滚策略。

## 2. 当前现象与结论
### 2.1 现象
- 目标在视距外时，雷达面板仍可扫描/选锁目标。
- 发射后导弹不再立即自毁（已修复），但会出现“直飞不导引”。
- 调试日志常见状态：`target=-1`、`dlRelay=true`、`captured=false`持续。
- 导弹配置中已启用`enableChunkLoader=true`，但问题仍可复现。

### 2.2 结论
- 问题核心不是“渲染视距”本身，而是“导弹制导链路与雷达显示链路解耦不完整”。
- `enableChunkLoader=true`只能保证导弹所在区块持续 Tick，不保证目标实体引用和中继数据持续有效。
- 因此会出现“雷达能看到目标，但导弹拿不到可制导目标”的链路断层。

## 3. 关键概念澄清
### 3.1 三条不同链路
- 雷达显示链路：可依赖`EntityInfo`快照/服务端同步，不一定依赖本地实体对象。
- 导弹制导链路：大量逻辑依赖`targetEntity`实体对象持续有效。
- RWR告警链路：威胁事件驱动，强调“谁在照我/锁我”，不等同雷达扫描缓存。

### 3.2 为什么区块加载不等于制导可用
- 区块加载解决的是“世界更新是否继续跑”，不是“目标实体是否可解析”和“数据链是否持续喂给导弹”。
- 当`targetId -> getEntityByID(targetId)`失败时，导弹会收到空目标并进入无导引或退化分支。

## 4. 当前代码链路（便于定位）
### 4.1 发射与目标绑定
- `MCH_WeaponAAMissile`发射时根据`option1`解析目标并调用`setTargetEntity`。
- 数据链模式下，后续目标刷新在`updateDataLinkTargetsFromRadar()`中进行。

### 4.2 数据链中继更新
- 现有逻辑会做`targetId > 0 ? world.getEntityByID(targetId) : null`。
- 若拿不到实体对象，会将目标视为`null`下发给导弹。
- 导弹筛选通过`getShootBullets(worldObj, user, range)`完成，存在作用域限制。

### 4.3 导弹自主行为
- `MCH_EntityAAMissile`在数据链模式下对`activeRadarCaptured`有门控。
- 当`captured=false`且未进入自主扫描分支时，导弹会表现为“活着但不导引”。

### 4.4 调试信号
- `mslwatch`日志可观察：
- `target`：当前目标实体ID；
- `dlRelay`：数据链中继开关；
- `captured`：主动雷达捕获状态；
- `chunk`：导弹所在区块加载状态。

## 5. 目标设计（最终状态）
### 5.1 功能目标
- 跨区块、互不渲染、多人服务器条件下，导弹保持稳定阶段性制导。
- 当实体暂不可用时，导弹可退化到快照坐标追踪，不出现“立即失智”。
- 当实体恢复可用时，自动回切实体追踪。
- 仅在“实体不可用且快照过期”时进入失效/惯导分支。

### 5.2 工程目标
- 优先低风险改造，避免大规模重构。
- 保持现有RWR、雷达、导弹配置兼容。
- 保留回滚开关，确保线上可控。

## 6. 分阶段实施方案
### 阶段A：先稳住（低风险，建议优先）
#### A1. 放宽导弹中继更新作用域
- 现状问题：仅以发射者为中心筛导弹，导弹飞远后掉出更新圈。
- 方案：
- 将导弹筛选改为“按发射者ID + 导弹类型”全局筛选，或以导弹当前位置分段筛选。
- 增加上限保护（例如每tick最多处理N枚）防止性能抖动。

#### A2. 引入短暂目标保活窗口
- 现状问题：单次`getEntityByID`失败就可能清空目标，链路抖动敏感。
- 方案：
- 对数据链目标增加保活计时（建议10~20 tick）。
- 窗口内若本tick拿不到实体，不立即清空目标，继续使用上次可用目标。

#### A3. 增强调试日志
- 在`mslwatch`中新增字段：
- `relaySrc=ENTITY|SNAPSHOT|NONE`
- `targetHoldTick`
- `relayReason`（例如`ENTITY_MISS_KEEP_HOLD`、`SNAPSHOT_USED`）

### 阶段B：双通道中继（中风险，收益大）
#### B1. 引入目标快照数据结构
- 建议新增`TargetTrackSnapshot`：
- `targetId`
- `posX/posY/posZ`
- `velX/velY/velZ`
- `heading/pitch`（可选）
- `lastUpdateTick`
- `source`（RADAR_TWS、RADAR_STT、RWR_BUS等）

#### B2. 中继优先级策略
- 优先级：`实体目标 > 快照目标 > 保活目标 > 失效`。
- 若实体可取：更新导弹`targetEntity`并刷新快照。
- 若实体不可取且快照新鲜：按快照坐标导引（预测点）。
- 若快照过期：进入阶段C定义的失效状态机。

#### B3. 发射门限修正
- 从“必须拿到本地实体”调整为“雷达选锁有效 + 快照新鲜”。
- 避免“雷达显示可发，实际被假拒射”的体验断层。

### 阶段C：主动弹状态机收敛（中高风险）
#### C1. 丢中继后的行为
- 主动雷达弹新增“延时自主扫描”：
- `relayLostGraceTick`内保持当前制导；
- 超时后自动尝试自主扫描；
- 捕获成功设置`captured=true`并进入自主导引。

#### C2. 统一失效流程
- 统一三段式：
- `KEEP`（保活）
- `REACQUIRE`（重捕获）
- `FAIL`（失效/惯导/自毁，按武器配置）

#### C3. 干扰联动
- ECM/Chaff作用应降低重捕获概率，不应直接让所有远距导弹瞬时“失智”。

## 7. 关键参数建议
### 7.1 新增可配置参数（建议）
- `DataLinkHoldTick = 15`
- `SnapshotFreshTick = 30`
- `ActiveRadarAutonomousScanDelayTick = 20`
- `MissileRelayUpdateLimitPerTick = 64`
- `EnableSnapshotGuidanceFallback = true`

### 7.2 参数解释
- `DataLinkHoldTick`：实体瞬时不可用时的保护时间。
- `SnapshotFreshTick`：快照是否可用于导引的最大年龄。
- `AutonomousScanDelay`：避免主动弹过早切自主扫描导致抖动。
- `UpdateLimit`：防止多人高负载时单tick处理过多导弹。

## 9. 验收测试计划
### 9.1 单人超视距
- 步骤：
- 在超视距条件下完成锁定并发射。
- 观察导弹是否保持导引、是否出现快照回退与重捕获日志。
- 通过标准：
- 不出现长时间“直飞无导引”；
- 失效必须可解释（日志有明确原因）。

### 9.2 双人跨区块（互不渲染）
- 场景：
- 玩家A与玩家B分处不同区块，A无法直接渲染B。
- A锁定B并发射导弹。
- 通过标准：
- 导弹应保持阶段性制导；
- 即便实体短时不可取，也应使用快照回退，随后可重捕获。

### 9.3 干扰与边界
- 场景：
- 目标开启ECM、释放Chaff、机动脱离。
- 通过标准：
- 导弹表现为“概率退化”而非“无条件立即失智”。

## 10. 性能与网络风险控制
### 10.1 性能风险
- 全局导弹筛选可能增加服务器负担。
- 控制策略：
- 分帧处理；
- 每tick处理上限；
- 仅处理“需要中继的雷达导弹”。

### 10.2 网络风险
- 快照同步若过量会挤占带宽。
- 控制策略：
- 仅同步关键目标摘要；
- 仅在目标变化显著时发送增量。

## 15. 爆炸特效扩展方案：`enableNuke`（纯粒子蘑菇云）
### 15.1 目标与约束
- 目标：新增`enableNuke=true`后启用“纯粒子蘑菇云”特效，不再依赖HBM核爆实体。
- 约束：只影响视觉表现，不改变现有爆炸伤害、破坏、网络判定链路。
- 约束：蘑菇云规模与`explosion`参数关联，保证配置直觉一致。
- 约束：在多人服和中低端客户端可控，不出现HBM核爆级卡顿。

### 15.2 现状链路结论（代码侧）
- 武器爆炸主链路：`MCH_EntityBaseBullet#newExplosion` -> `MCH_Explosion.newExplosion(...)`。
- 现有核爆特效触发点：`MCH_EntityBaseBullet`中通过`nukeYield > 0 && MCH_HBMUtil.isHBMLoaded`调用HBM的`EntityNukeExplosionMK5/EntityNukeTorex`。
- 项目内已存在自研`EntityNukeTorex + RenderTorex`，但渲染纹理资源路径仍指向`hbm:`域，不适合作为“无HBM依赖”的最终形态。
- 结论：可复用现有Torex结构（云团生命周期/分层运动）作为骨架，但需完成“资源去HBM化 + 触发链路独立化 + 性能分级”。

### 15.3 参数与数据结构建议
- 在`MCH_WeaponInfo`新增：
- `EnableNuke = false`（布尔开关，默认关）。
- `NukeEffectScale = 1.0`（可选，范围建议`0.25~4.0`，用于微调视觉大小）。
- `NukeEffectType = 0`（可选，预留标准/沙尘等样式）。
- 保留兼容：
- `nukeYield`继续保留给HBM链路，不与`enableNuke`互斥。
- 优先级建议：`enableNuke=true`时优先走自研纯粒子；`enableNuke=false`时维持现状。
- 尺度映射建议（核心）：
- `nukeScale = clamp(sqrt(max(1, explosion)) * 0.22 * NukeEffectScale, 0.6, 6.0)`。
- 说明：使用`sqrt`而非线性，避免大爆炸特效尺寸和粒子数失控。

### 15.4 触发与同步方案（推荐最小侵入）
- 触发位置：在`MCH_EntityBaseBullet`爆炸完成后判定`getInfo().enableNuke`，服务端生成“核爆视觉事件”。
- 同步方式（二选一）：
- 方案A（推荐）：新增`MCH_PacketEffectNuke`，字段仅包含`x/y/z, explosionSize, effectScale, type`，客户端据此生成特效实体。
- 方案B：扩展现有`MCH_PacketEffectExplosion`增加`isNuke/type`字段，减少包类型但改动面更广。
- 客户端表现：
- 仅客户端生成`EntityNukeTorex`（或其轻量版），服务端不维护复杂粒子状态。
- 可保留一个极简服务端占位实体用于追踪范围同步，但不建议在服务端跑云团模拟。

### 15.5 纯粒子蘑菇云渲染分层
- 阶段1（0~10 tick）：爆心闪光 + 地面冲击环（低粒子，高亮，短寿命）。
- 阶段2（10~120 tick）：主云柱快速抬升（中粒子，纵向速度主导）。
- 阶段3（120~400 tick）：伞盖展开（中高粒子，水平扩散 + 轻旋涡）。
- 阶段4（400+ tick）：衰减与泛灰（低粒子，透明度退场）。
- 粒子类型建议：
- 近景主云：billboard smoke（自定义纹理）。
- 冲击环：环形薄片/稀疏云片（短生命周期）。
- 爆心：additive flare（限制持续时间，避免过曝）。

### 15.6 性能控制（重点）
- 硬上限：每次核爆云团粒子上限`maxCloudlets`，建议按画质分档：
- `ALL=700`, `DECREASED=380`, `MINIMAL=180`（可根据实测调整）。
- 距离LOD：
- 近距离（<128m）全量；
- 中距离（128~256m）减半；
- 远距离（>256m）仅保留伞盖主体与闪光残留。
- 时间分帧：
- 每tick生成数做上限，避免首帧突发分配造成卡顿尖峰。
- 纹理与混合：
- 使用`mcheli`域内本地纹理，避免外部模组资源查找开销；
- 透明混合前按距离排序（已有`RenderTorex`思路可复用）。
- 防叠加雪崩：
- 同一半径内短时间多次触发时合并/降级（例如2秒内第二次只生成70%粒子）。

### 15.9 核爆闪光（视网膜损伤模拟）扩展
- 目标：对爆炸范围内玩家叠加“黄白色核闪”屏幕特效，形成“由浅到深再到浅、由半透明到不透明再到半透明”的视觉曲线。
- 触发范围：仅对`distance <= flashRadius`的玩家生效，`flashRadius`建议与蘑菇云共用尺度源：
- `flashRadius = explosion * 14.0`（可按实测改为`12.0~18.0`区间）。
- 时长规则（满足20~80 tick，越近越久）：
- `dist01 = clamp(distance / flashRadius, 0, 1)`
- `pow01 = clamp(explosion / 40.0, 0, 1)`
- `durationTick = clamp(round(20 + 60 * (0.65 * pow01 + 0.35 * (1 - dist01) * (1 - dist01))), 20, 80)`
- 透明度规则（半透明 -> 不透明 -> 半透明）：
- `baseAlpha = 0.22`
- `peakAlpha = clamp(0.55 + 0.40 * (0.70 * pow01 + 0.30 * (1 - dist01)), 0.55, 0.95)`
- 令`t = elapsedTick / durationTick`，使用平滑脉冲：`pulse = sin(pi * t)`（0->1->0），最终`alpha = lerp(baseAlpha, peakAlpha, pulse)`。
- 颜色规则（黄白渐变）：
- 起始色：`(1.00, 0.98, 0.86)`（暖白偏黄）；
- 峰值色：`(1.00, 1.00, 0.94)`（更亮的黄白）；
- 退场色回到起始色，颜色插值同样可复用`pulse`。
- 网络与实现建议：
- 服务端仅广播一次`NukeFlash`事件（中心点、`explosion`、时间戳），客户端按本地距离计算每名玩家自己的`duration/alpha`。
- 客户端在HUD Overlay阶段渲染全屏半透明色层（不改世界光照），避免与粒子系统耦合。
- 可选增强：
- 若有遮挡检测（墙体/地形），可对`peakAlpha`施加`0.5~0.8`衰减；
- 与夜视/热成像模式叠加时，建议上限`alpha <= 0.85`避免完全不可见。
- 验收标准：
- 近距离玩家核闪持续时间明显长于远距离玩家，且严格落在`20~80 tick`；
- 全程呈现“浅->深->浅”的连续变化，不出现突变闪烁；
- 多人同时受影响时无明显卡顿（HUD叠层不应引入粒子级性能负担）。
