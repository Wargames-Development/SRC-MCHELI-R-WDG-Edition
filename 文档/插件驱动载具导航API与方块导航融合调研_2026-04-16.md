# 插件驱动载具导航 API 与方块导航融合调研

日期：2026-04-16  
范围：需求整理与架构方案（不改代码）

---

## 1. 你朋友建议的核心诉求（整理）

- 希望支持“插件层导入导航点集合”，不只依赖方块。
- 希望提供“导入坐标接口”，来源可选：
  - 方块采集
  - 插件直接传入
- 希望提供一个可调用方法：
  - 入参：`载具实体 + 有序导航点列表`
- 希望把“载具当前各种 gunner 的 AI 逻辑”和“gunner 实体本身”解耦。
- 解耦范围包含：运动、索敌、攻击等行为，不再依赖“gunner 实体骑乘”才能工作。
- gunner 可保留为“AI 启动开关/配置载体”，而非 AI 主体。
- 原话意图：`ai炮手最好别走实体逻辑，把ai炮手当成载具的一部分，抽象一层即可。`
- 目标是未来可由插件直接驱动载具巡逻/导航。

---

## 2. 总体方向：双来源导航 + 统一导航内核

建议做成两层：

- 上层“数据来源层”
  - `BlockSource`：从航路点方块读取链路
  - `PluginSource`：插件直接传有序点列表
- 下层“导航执行层”
  - 不关心来源，只执行统一状态机：
  - `NAVIGATE -> HOLD -> NAVIGATE ... / FINISHED`

这样后续切换来源不会动底层运动逻辑。

## 3. API 设计草案（给插件调用）

### 3.1 数据结构（建议）

```java
public final class MCH_NavPoint {
    public final String id;
    public final double x;
    public final double y;
    public final double z;
    public final double radius;
    public final double height;
    public final int holdTick;
    public final boolean terminator;
}
```

```java
public final class MCH_NavigationRequest {
    public final Entity vehicle;
    public final List<MCH_NavPoint> points; // 有序列表
    public final boolean loop;
    public final boolean holdAsFreeState;
    public final boolean suppressLargeTurnInNavigate;
}
```

### 3.2 对外 API（建议）

```java
public interface IMCH_NavigationApi {
    boolean startNavigation(MCH_NavigationRequest req);
    boolean stopNavigation(Entity vehicle, String reason);
    boolean pauseNavigation(Entity vehicle);
    boolean resumeNavigation(Entity vehicle);
    MCH_NavigationStatus getStatus(Entity vehicle);
}
```

最低必需接口（你朋友提的版本）可先简化为：

```java
boolean startNavigation(Entity vehicle, List<MCH_NavPoint> orderedPoints);
```

## 4. 与方块导航的融合方式

建议不是做两套系统，而是：

- 方块链路把配置转成 `List<MCH_NavPoint>`，调用同一个 `startNavigation(...)`
- 插件链路直接构造 `List<MCH_NavPoint>`，调用同一个 `startNavigation(...)`

收益：

- 统一行为，方便排查
- 调试命令、渲染、日志全部复用
- 后续维护成本低

---

## 5. “载具AI炮手 与 gunner实体”解耦建议

建议拆成两层：

- `VehicleAIPilotController`（载具内置AI层）
  - 负责运动、索敌、攻击、武器调度
  - 生命周期与载具绑定，不依赖 gunner 实体是否存在
- `GunnerEntityAdapter`（实体适配层）
  - 负责“是否启用AI”“阵营/规则参数注入”“可视化表现”
  - 可选存在，作为开关与交互入口，而非核心AI执行体

两层通过“配置与状态”交互：

- 载具AI读取 gunner/profile/方块配置得到策略参数
- gunner 实体仅改变 `enabled/disabled` 与参数集，不直接跑主AI循环

这样可避免“实体骑乘状态异常”导致 AI 失效，并降低多人环境同步复杂度。

---

## 6. 导航数据导入模式建议

建议支持 3 种模式：

1. `BLOCK_ONLY`  
   - 仅方块链路生成路线
2. `PLUGIN_ONLY`  
   - 仅插件传入路线
3. `PLUGIN_OVERRIDE_BLOCK`  
   - 有插件任务时覆盖方块路线，无任务时回退方块

---

## 7. 调试与可观测性（建议）

为插件时代提前准备：

- 命令：`/mcheli debug waypoint true|false`
- 日志：`logs/mcheli_waypoint_debug.log`
- 渲染：航路点上方显示 `当前点→下一点`
- 查询：右键方块显示当前点/下一点及坐标
- API 状态查询：`getStatus(vehicle)` 返回：
  - 当前状态
  - 当前点索引
  - 剩余 hold tick
  - 失败原因

## 8. 兼容与风险评估

- 风险1：插件传入非法点（空列表/坐标异常）
  - 方案：`startNavigation` 入参校验，失败返回 false + reason

- 风险2：载具被销毁/卸载区块
  - 方案：状态自动转 `FINISHED/ERROR`，可配置重试

- 风险3：多系统抢控制权（玩家手动驾驶 vs 插件导航）
  - 方案：增加控制优先级与抢占策略：
  - `manual > plugin > block`（建议默认）

- 风险4：与 gunner 行为耦合回归
  - 方案：把AI主循环固定在载具侧；gunner实体仅做开关与参数输入

- 风险5：历史内容大量依赖 `MCH_EntityGunner` 逻辑
  - 方案：先加 `Adapter` 兼容层，分阶段迁移索敌/攻击/运动，不一次性替换

---

## 9. 建议落地路线（面向将来插件化）

### Phase 1（当前版本）
- 先做统一导航内核（状态机 + 运动接管）
- 方块链路接入
- debug 命令/渲染/右键查询接入

### Phase 2（API 初版）
- 暴露 `startNavigation(vehicle, orderedPoints)` 最小 API
- 补 `stop/getStatus`
- 增加入参校验和错误码

### Phase 3（插件增强）
- 加入优先级抢占策略
- 支持 pause/resume
- 支持多任务队列（可选）

### Phase 4（仅调研预留：AI炮手解耦）
- 新增 `VehicleAIPilotController` 抽象层
- 先迁移“索敌+攻击”到载具侧
- 再迁移“运动决策”到载具侧
- gunner 实体保留为开关与参数容器（可逐步弱化）

---

## 10. 结论

- 你朋友的建议方向非常好，且与当前“方块航路点”并不冲突。
- 最优做法是“统一导航内核 + 双来源接入（方块/插件）”。
- 提前设计 API 是值得的，后续插件驱动载具时可以直接复用，不需要推翻方块系统。
- 关于“AI炮手实体化”问题：建议长期演进为“载具内置AI + gunner开关/参数适配层”，但当前阶段先做调研与接口预留，不立即重构。
