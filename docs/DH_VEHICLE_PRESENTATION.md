# DH vehicle source adapter

Work branch: feature/dh-lods. The optional common API currently captures visual state only; it does not claim rendering or disable any legacy entry point. Radar/entity-info packets, tracking, locks, WGMap and existing renderers are unchanged.

`MCH_ExternalVehiclePresentation` API v1 captures supported live, visible, undestroyed helicopter, plane, tank and vehicle classes on the server thread. `MCH_VehicleVisualSnapshot` is immutable, versioned and limited to 512 bytes: identity, asset names, position, body/turret orientation, source rotor phase, hatch/canopy/gear, plane nozzle/wing, throttle, occupancy/steering/ground flags and saved lighting. Asset names, UTF-8, counts, numeric values and part angles are checked at the boundary. Light access first proves the chunk is loaded; capture does not query altitude, generate chunks or call the radar snapshot helper.

Server source audit found meaningful rotor phase updates on both server and client, but wheel, track and generic rotating-part fields have client-only update guards. Those frozen server arrays are deliberately absent from this contract. The DH client provider must derive their cosmetic animation from valid source inputs using the existing content rules, or extend this adapter with an explicit shared animation kernel. It must not advertise complete animation parity from these initial fields alone. Texture/model bounds, folded blades, weapon recoil, tracks/wheels, carried vehicles, private cameras and thermal views remain acceptance work.

Workflow review: B1, the minimum legal one-character asset envelope is 107 bytes, corrected before testing. B2, client-only part arrays cannot stand in for authoritative animation, excluded after inspecting the source update guards. T1, transport/render ownership and runtime model acceptance remain pending. The read-only API cannot disable legacy delivery or rendering by itself.

Validation: Java 8 `compileJava test --offline` passed 228 tests across 45 suites. Four new tests cover pose/identity round trips and defensive copies, all truncated lengths and malformed envelopes/UTF-8, invalid assets/numerics, and direct server-capture bytecode checks against client calls, world simulation and chunk-generation APIs. These tests do not replace a dedicated-server/client launch.

Next in-game acceptance, once the DH provider is wired: compare the same vehicle crossing native tracking range at 750 blocks and the configured server ceiling; check body/turret/gear/rotor and all content-specific parts, terrain gaps and partial cover, respawn/dimension/world changes, destroyed/reused identities, shaderless/Angelica, FMUR scopes/thermal cameras and MCHELI remote views. Keep the old path available until those pass.

The API also exposes a cheap read-only `eligible(Entity)` check so DH can exclude wrecks/invisible/unsupported aircraft before bounded nearest-recipient selection, without allocating/lighting every candidate. Capture repeats eligibility internally as its boundary check. Existing API callers and all legacy paths remain unchanged. The full compile/test suite passed again after this addition.

API/snapshot v2 adds an exact double-precision unwrapped rotor phase. The existing rotor update observes its actual step in a separate cosmetic counter; it never reads that counter for flight, weapons or native rotation. No saved field was added. The four-sample `MCH_VehicleVisualTrack` interpolates that phase directly, preserving fast, reverse and multiple-turn motion without guessing the number of revolutions. Body/turret/gear/appearance share the same timeline, which expires, rejects late frames and resets teleports or identity changes. Compilation/tests passed 234 tests across 46 suites, with six new timeline tests including all update intervals, long-uptime precision and multiple/reverse rotor turns. The DH bridge requires API v2; earlier experimental source adapters are withheld. Vehicle model ownership/rendering remains pending.

## Experimental client model adapter (API v3)

The bounded part payload now supplies weapon transforms, loaded ammunition/cooldown masks, recoil, bays, blade/fold positions, ERA panels and visual control/light inputs. Maximum source payload is 4 KiB; DH's matching experimental channel v2 enforces a 24 KiB whole-entry frame budget. No gameplay/radar packet was replaced.

`MCH_ExternalVehicleRenderer` supplies optional ownership callbacks, detached model contexts and the existing guidance laser-cache bridge. Without an explicit compatible provider registration, legacy ownership stays unchanged. Contexts never join a world or run aircraft/weapon updates. Native model/part methods draw source-confirmed state; ordinary tracked models remain usable while far handoff is controlled by the provider. No WGMap source is changed, and its existing laser gameplay validation remains independent of DH visual occlusion. The detached adapter skips cockpit radar/RWR displays, ropes and volumetric searchlight output. Model envelopes conservatively include pivots, children, recoil, slides and crawler paths; missing/cyclic or >128-block envelopes withhold the model.

The DH integration remains behind `-Ddh.experimentalMcheliModels=true` pending real pack validation. This is not a completed migration or a promise of every custom animation/material/auxiliary-camera path. Native rotor rotation and saved formats remain unchanged. Validation: Java 8 compile plus all 244 tests (49 suites) passed; new cases cover source part payloads, bounds over rotations and child pivots, cyclic assets, ownership defaults and absence of gameplay/world/network update calls from contexts. Source/client model layout mismatch is withheld. Actual Minecraft, shaderpack, guidance, scope and thermal acceptance remains outstanding.
